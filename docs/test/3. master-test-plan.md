# 🗺️ Master Test Plan - Góc Nhìn QA Senior

**Dự án:** ChatHub Real-Time System  
**Người lập kế hoạch:** Senior QA / SDET Lead (Tác giả)  
**Mục tiêu (Objective):** Đảm bảo hệ thống vận hành trơn tru ở cường độ cao, không đứt gãy trạng thái nội bộ (WebRTC/Socket), trải nghiệm 0-latency. Đặc biệt **bảo hiểm Codebase tuyệt đối** để không bao giờ xảy ra Conflict hay lỗi gãy vỡ (Crash) khi Deploy lên Production.

---

## 1. Phạm Vi Kiểm Thử (Testing Scope)

Để bao phủ toàn bộ kiến trúc MERN + WebRTC + Redis, chiến lược kiểm thử (Testing Pyramid) được chia làm 4 lớp:

1.  **Unit Tests (Khối lượng lớn nhất - Xử lý bởi Dev):** 
    *   Hành vi của Zustand Store (`useCallStore`, `useChatStore`).
    *   Các Utility Functions (định dạng ngày, parse Base64 ảnh).
2.  **Integration Tests (Khối lượng trung bình):**
    *   REST API Endpoints (Auth, Messages).
    *   Luồng Pub/Sub giữa Socket.IO và Redis Adapter.
3.  **End-to-End Tests (E2E) (Khối lượng nhỏ - Dành cho Luồng User cốt lõi):**
    *   Quy trình Đăng ký -> Đăng nhập -> Chat -> Gọi điện -> Tắt máy.
4.  **Non-Functional Tests (Kiểm thử phi chức năng):**
    *   **Load Testing:** Bắn 500 requests Call/phút xem Redis chặn Rate-Limit có sập Node.js không.
    *   **Chaos Testing:** Thử ngắt MongoDB xem Firebase/Socket có crash toàn App hay không (Expected: Báo lỗi thanh lịch).

## 3. Quản Lý Thiết Bị / Môi Trường Test (Test Environment & Devices)

Việc Test Real-time cực kỳ nhạy cảm với nền tảng phần cứng vì cơ chế xử lý background tab của từng OS khác nhau. QA Lead cần lên lịch Audit (E2E Manual/Automated) trên các Matrix sau:

*   **Trình duyệt Máy tính:** 
    - Google Chrome (Tiêu chuẩn).
    - Safari MacOS (Thích chặn WebRTC do vụ Auto-Play Muted Policy -> Cần bắt exception permission).
*   **Trình duyệt Di động (Mobile Web View):**
    - iOS Safari Tab ẩn (Background Tab): Tab bị đóng băng Socket sau 30s. Kịch bản khôi phục khi mở lại Tab.
*   **Mạng Yếu (Network Throttling):** Giả lập 3G trong Chrome DevTool để đo thời gian tải ảnh Cloudinary và ping độ trễ STUN Server.

## 4. Định Hướng CI/CD (Bảo Vệ Code Lên Production)

Để đảm bảo không Developer nào (kể cả QA) vô tình đẩy Code rác lên GitHub làm chết hệ thống:

1.  **Dựng Pre-commit Hook (Husky):** Mỗi khi gõ lệnh `git commit`, hệ thống tự động chạy `npm run test`. Nếu 1 test fail, cấm commit.
2.  **GitHub Actions:** Khi Push lên nhánh nhánh `main`, Server GitHub cấp phát một môi trường Ubuntu:
    * Pull Source Code.
    * Tạo MongoDB Memory Server.
    * Cài Dependency và Chạy `npm run test` Backend/Frontend.
    * Gửi Mail báo cáo (hoặc block Merge Request).

## 5. Tiêu Chuẩn Phê Duyệt (Checklist Push Code & Create PR)

Để triệt tiêu khái niệm "Lỗi vặt" và "Conflict" khi Deploy lên các môi trường (Staging/Production), mọi Developer trước khi Push Code hoặc tạo Pull Request (PR) phải tuân thủ nghiêm ngặt 4 bước:

- [ ] **Check Code Local (Pre-Flight):** Máy cá nhân phải chạy thành công `npm run build` ở Frontend tránh lỗi syntax ES6/Tailwind.
- [ ] **Pass All Tests:** Lệnh `npm test` ở cả Backend và Frontend phải trả về 100% Pass. Bất kỳ Test nào bị FAIL (Dù là liên quan đến Feature khác) cũng **nghiêm cấm Push**.
- [ ] **Sync Branch:** Luôn phải Git Pull nhánh `main` mới nhất về nhánh làm việc cá nhân và giải quyết (Resolve) mọi Conflict ở máy Local.
- [ ] **Quy chuẩn PR:** Tạo Pull Request với Title rõ ràng (Vd: `feat(webrtc): Fix 3rd-person call bug`). Gắn bằng chứng (Hình ảnh Pass Test hoặc Terminal) vào Description của PR để Reviewer duyệt nhanh chóng.

## 6. Q&A: Nỗi Lo "Phình To" Thư Mục Test

**Câu hỏi:** *Nếu dự án mở rộng, sau này có tới hàng trăm, hàng ngàn file Test thì Source Code liệu có bị rối tung (Messy) hay khó quản lý không?*

**Senior SDET Giải đáp:** Hoàn toàn **KHÔNG**. 

Ngược lại, càng nhiều Test hệ thống càng vững chắc như một thành trì. Để không bị "ngộp" bởi hàng ngàn file Test, chúng ta đang bảo chứng bằng nguyên tắc **Colocation (Định vị cục bộ)** đã quy định ở file hướng dẫn:
1.  **File Test nằm ở đâu, Code nằm ở đó:** File `auth.controller.js` sẽ luôn đi kèm thư mục `__tests__/auth.controller.test.js` ngay sát bên. Bạn đang sửa logic của File nào, bạn chỉ quan sát file Test của chính File đó. Không có một thư mục `/tests/` khổng lồ tập trung rác thải.
2.  **Vitest / Jest cực kỳ thông minh:** Khi bạn dùng lệnh `npm test --watch`, nó chỉ chạy Test trên những file mà bạn **vừa chạm tay sửa đổi (Changed files only)**. Bạn có 10,000 file Test, nhưng nếu bạn sửa mã nguồn ở `useCallStore`, Vite/Jest chỉ tốn 0.5s để chạy lại mỗi file `useCallStore.test.js`.
3.  **Bảo hiểm trọn đời:** Hàng ngàn file Test đó chính là hàng ngàn "Con BOT Tester" chạy ngầm ban đêm thay vì cần 1 đội QA bấm tay mỏi mệt. Khi bạn lỡ tay làm gãy một Feature cách đây 2 năm, BOT sẽ réo lên chặn tay bạn mắng "Đừng Push!". Sự rối rắm là thứ không bao giờ xảy ra đối với các công ty Big Tech nhờ Tester ảo này.
